# 22. Операции с проектом: `save_as_project`, блокировка, `connect`

Исполнитель: Sonnet. Приоритет: высокий, дефект и две проверки (независимое тестирование).
Объём: средний. Риск для TIA Portal: средний — открытие, закрытие и сохранение проекта.

Работать на **копии** проверочного проекта или на временном проекте: `save_as_project`
переключает TIA Portal на новый путь. После проверки вернуть TIA Portal на проверочный проект
(`tools/start-tia.ps1` либо `open_project`), а созданные папки перечислить Biz — удалить их
среда может не дать.

## А. `save_as_project` и расширение в пути — дефект

`Portal.SaveAsProject(string path)` (`Siemens/Portal.cs`) делает `new DirectoryInfo(path)` и
`Project.SaveAs(di)` без проверок. Факты из отчёта тестирования:

- путь `...\X.ap21` создаёт папку `X.ap21` с файлом `X.ap21.ap21`;
- путь с расширением внутри уже существующей папки завершается ошибкой TIA Portal «storage
  medium is no longer available»;
- путь без расширения работает.

Сделать:

1. Путь, оканчивающийся на расширение проекта (`.ap\d+`, `.als\d+`), отклонять с
   `InvalidParams` и объяснением: «это папка нового проекта; файл `<имя>.ap21` TIA Portal
   создаст в ней сам» с готовым исправленным путём в тексте. Не отрезать молча: вызывающий
   должен знать, куда лёг проект.
2. До обращения к Openness проверять: путь абсолютный; родительская папка существует; целевая
   папка не существует либо пуста.
3. Описание параметра: «папка нового проекта, без расширения».
4. В ответе вернуть полный путь получившегося файла проекта.

## Б. Общий каркас и блокировка — проверить и исправить

`OpenProject`, `SaveProject`, `SaveAsProject`, `CloseProject` — старые методы: возвращают
`bool`, ошибки глотают (`catch (Exception) { return false; }`), **не идут через
`Operation.Run`**, то есть не берут общую блокировку. Тестировщик вызвал `save_as_project` и
`get_project_tree` одновременно; сбоя не было, но ничто его не предотвращает.

1. Перевести четыре метода на `Operation.Run` с `PortalException` (образцы — любой метод в
   `Portal.Unified*.cs`; коды — `docs/error-model.md`). Причина отказа должна доходить до
   вызывающего текстом, а не превращаться в `false`.
2. Убедиться чтением кода `Operation.cs`, что блокировка одна на все операции и что её берут
   и чтения. Проверить то же для методов сессий (`Portal.cs`, регион `session`).
3. Проверить вживую: параллельные `save_project` и `get_project_tree` (два вызова в одном
   процессе сервера идут по очереди) — оба успешны, порядок не важен.
4. `close_project` во время чтения: чтение, начавшееся раньше, заканчивается; начавшееся позже
   отвечает `InvalidState` «проект не открыт», а не исключением об освобождённом объекте.

## В. `connect` без параметров — проверить

В отчёте: сервер сообщал `Connected=false` при открытом TIA Portal; подключение прошло после
`connect` с PID. Неясно, вызывался ли `connect` без параметров.

1. Проверить одним вызовом при одном запущенном экземпляре: `connect` без параметров обязан
   подключиться. Если подключается — записать это в файл задачи и закрыть пункт.
2. `TiaInstanceSelection.Pick` без критериев берёт `instances[0]`, а `ConnectPortal` —
   `processes.First()`. При двух экземплярах первым может оказаться пустой. Изменить: без
   критериев предпочитать единственный экземпляр с открытым проектом; если с проектом
   несколько — отказывать `InvalidParams` со списком (как при неоднозначном `projectPath`);
   если проектов нет ни в одном — первый, как сейчас. Логику держать в `TiaInstanceSelection`
   (она чистая), тесты — в `Test26InstanceSelection.cs`.
3. `get_state` при неподключённом сервере: в `note` подсказать «вызовите `connect`» и назвать
   запущенные экземпляры, если они есть.

## Готово, когда

- Три пути `save_as_project` (с расширением, в существующую непустую папку, правильный) дают
  понятный результат; проверено вживую на копии.
- Четыре операции проекта идут через `Operation.Run`; отказ TIA Portal виден текстом.
- Тесты выбора экземпляра покрывают новые случаи; `connect` без параметров проверен вживую.
- `CHANGELOG.md` (поведение `connect` без параметров при нескольких экземплярах — в
  «Changed»), `README.md` / `README_ru.md`, строки в `../PLAN.md` отмечены.

## Риски

- `Project.SaveAs` меняет путь открытого проекта. Не выполнять на проверочном проекте без
  копии.
- Открыт может быть `TestProject` (проект тестировщика) — перед записью проверить `get_project`.

## Результат (06.10.2026)

**А. `save_as_project`.** Правила в чистом классе `ProjectPathRules` (абсолютный путь; расширение `.apXX`/`.alsXX` отклоняется с готовым
исправленным путём и путём будущего файла; родительская папка существует; целевая не существует или пуста). Ответ несёт `path` —
полный путь файла проекта. Проверено вживую на 473 МБ копии проверочного проекта: `...\Copy1.ap21` — `InvalidParams` с исправлением;
относительный путь, несуществующий родитель, непустая папка (сама папка проверочного проекта) — отказ без записи; `...\MCPT_SaveAs\Copy1` —
готово за 4 с, TIA Portal переключился на копию, файл `Copy1\Copy1.ap21`; повторный вызов в ту же папку — «не пуста». Затем
`open_project` вернул проверочный проект, временная папка `C:\Users\Biz\Desktop\MCPT_SaveAs` удалена. Тесты `Test27ProjectPath` (6).

**Б. Каркас и блокировка.**
- `OpenProject`, `SaveProject`, `SaveAsProject`, `CloseProject` и методы сессий — через `Operation.Run`, бросают `PortalException`
  (`InvalidState`, у `open_project` с несуществующим файлом — `NotFound`); `RequireProject` / `RequirePortal` / `RequireSession`.
  Многопользовательский проект — `NotSupported` с пояснением. Раньше `OpenProject` при неверном пути молча отвечал `false`.
- Чтение кода: блокировка в `Operation.cs` одна (`Monitor`, реентерабельная). Её **не брали** `GetState`, `GetProjects`,
  `GetProjectInfo`, `GetSessions`, `GetProjectTree`, `GetDevices`/`GetDevice`/`GetDeviceItem`, `GetPlcSoftware`,
  `GetSoftwareContainer`, `CompileSoftware`, `GetSoftwareTree`, `ConnectPortal`, `DisconnectPortal`, а `InTransaction` брала её только
  вложенными вызовами. Все они теперь под `Operation.Locked` (`Portal.Locking.cs`: старые тела стали приватными `...Unlocked`),
  транзакция держит блокировку целиком.
- **Пункт 4 одной блокировкой не решался:** инструмент продолжает пользоваться объектами Openness (устройства, блоки) после выхода из
  метода `Portal`, и параллельный `close_project` освобождал их под ним. Живьём получилось: `hw_get_devices` → «Access to a disposed
  object of type DeviceImpl». Поэтому добавлен `ToolCallGate` (`ModelContextProtocol/ToolCallGate.cs`, фильтр `AddCallToolFilter` SDK):
  вызовы инструментов идут по одному, кроме `get_state`, `get_tia_instances`, `doctor`. Цена: долгий вызов (загрузка, компиляция)
  задерживает остальные — до этого они упирались в ту же блокировку внутри `Operation.Run`.
- Живая проверка параллельных вызовов (`par.py` — клиент, который шлёт вызовы одновременно, в каталоге временных файлов):
  `save_project` + `get_project_tree` + `plc_get_cross_references` + `hw_get_devices` — все успешны, идут по очереди (+1,7…2,1 с);
  `get_project_tree` + `plc_get_cross_references` + `close_project` + `hw_get_devices` + `get_project_tree` — начавшиеся раньше закрытия
  отвечают данными, начавшиеся позже — `InvalidState` «No project is open», ни одного «disposed object» (два прогона, порядок разный).
  `get_project_tree` без проекта раньше отвечал «Failed retrieving project tree», `hw_get_devices` — пустым списком; теперь оба
  `InvalidState` с причиной.

**В. `connect`.**
1. Без параметров при одном экземпляре — подключается (проверено вживую).
2. `TiaInstanceSelection.Pick` без критериев: единственный экземпляр с проектом; нигде нет проекта — первый; проектов несколько —
   `InvalidParams` со списком. `ConnectPortal` теперь всегда идёт через `Pick`. Тесты в `Test26InstanceSelection` (+4). При двух
   экземплярах вживую это не повторялось (второй TIA не открывался) — проверено тестами и тем, что с одним экземпляром путь тот же.
3. `get_state` без подключения: `note` с «вызовите `connect`» и перечнем запущенных экземпляров (проверено вживую).

В `get_state` в начале вызова `Project` может показать ещё открытый проект, если параллельный `close_project` стоит в очереди позже: `get_state`
идёт мимо очереди намеренно.
