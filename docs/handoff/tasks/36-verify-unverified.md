# 36. Проверить вживую то, что проверено только тестами

Исполнитель: Sonnet. Приоритет: средний. Объём: небольшой. Риск для TIA Portal: низкий.

Задача-список: пункты независимы, один пункт — один коммит (или запись в план, если код не
менялся). Для каждого пункта написать прямо: проверено вживую и что получилось, либо почему
проверить нельзя.

## Пункты

1. **Кросс-ссылки пользовательских констант.** В проверочном проекте констант не было, служба
   `CrossReferenceService` у них не проверена (`findings.md`, раздел 21). Создать константу
   `MCPT_Const` (`plc_create_user_constant`) во временной таблице, использовать её в блоке
   `MCPT_` (SCL), скомпилировать; `plc_get_cross_references` и `plc_where_used` по константе.
   Если службы нет — отказ инструмента должен говорить это, а не «не найдено».
2. **Страницы `unified_get_alarms` на панели.** На `HMI Unified/HMI_RT_3` алармов нет. Создать
   `unified_manage_alarms` 12 дискретных алармов `MCPT_`, прочитать с `limit` 5: страницы
   5+5+2, `nextOffset`, `total`; удалить. На ПК-станции `АРМ Unified/HMI_RT_1` 368 алармов —
   там же проверить страницу по умолчанию и `limit` 100.
3. **`protect_all` / `unprotect_all`** защиты конфиденциальных данных
   (`sec_set_plc_configuration_protection`). Вживую проверены не на всех CPU: найти чтением
   `sec_get_plc_security` CPU, который их поддерживает, на временной станции `MCPT_` (S7-1500
   V2.9 и V4.0 создаются из каталога) выполнить оба и прочитать обратно. Пароль — тестовый,
   только на временном ПЛК.
4. **`connect` при двух экземплярах TIA Portal** (`findings.md`, раздел 22). **Нужен Biz:**
   второй экземпляр TIA Portal (пустой, без проекта) запускает он или разрешает запустить -
   спросить. `connect` без параметров выбирает экземпляр с проектом; `get_tia_instances`
   показывает оба. Второй экземпляр закрыть.
5. **Предел страницы по умолчанию (500)** вживую не срабатывал: больше 500 записей в проекте
   только у тегов. `unified_get_tags` (2556) без `limit` — страница, `nextOffset`, сумма страниц
   равна `total`.
6. **`plc_get_technology_objects` на ПЛК проверочного проекта.** Инструменты проверялись на
   временном CPU 1511. Прочитать список на `PLC (A0)`, `PLC (A5)` и третьем ПЛК, для одного
   объекта каждого вида — параметры; сверить число с деревом (`plc_get_software_tree`).
   Только чтение.

## Чего не делать

`plc_replace_source` (непроверенное по нему — работа Opus), загрузку в ПЛК (нужен PLCSIM,
запускает Biz), `sec_protect_project`.

## Готово, когда

По каждому пункту в этом файле записан итог; строка «Не проверено вживую» в `../../PLAN.md`
сокращена до того, что осталось.

## Результаты (08.10.2026)

### Пункт 5 — предел страницы

Проверено вживую (`inproc-call`, панель `HMI_RT_3`, 2556 HMI-тегов). Предел по умолчанию 500 в проекте не сработает ни у одного списка: у `unified_get_tags` умолчание 200, у `plc_get_tags` 200, остальные
списки короче 500 (самый длинный — 368 алармов ПК-станции). Поэтому проверен механизм: без `limit` — страница 200, `truncated: true`, `nextOffset: 200`; 13 страниц подряд (`offset` 0, 200 ... 2400) дали
2556 записей и 2556 разных имён = `total`; `limit: 500` — страница ровно 500, `nextOffset: 500`; `limit: 0` — все 2556; `offset` за концом — пустая страница. Найдено и исправлено: на пустой странице
за концом сообщение гласило «Items 10000 to 9999 of 2556» — теперь «The offset 9999 is past the end: the list has 2556 item(s), the last offset is 2555» (`ListPage.Note`, тест `Test_2599`).

### Пункт 2 — страницы `unified_get_alarms`

Проверено вживую (`inproc-call`). Панель `HMI_RT_3`: таблица `MCPT_TTA`, тег `MCPT_TagW` (Word), класс `MCPT_AC`, 12 дискретных алармов `MCPT_Al00`–`MCPT_Al11` (биты 0–11) одним пакетом; `limit: 5` — страницы 5 + 5 + 2
(`total` 12, `nextOffset` 5, 10, у последней нет; `offset: 15` — пустая страница, `total` 12); фильтр `nameFilter: MCPT_` — все 12; всё удалено, алармов на панели снова 0. ПК-станция `HMI_RT_1`
(368 алармов): `limit: 100` — 100 + 100 + 100 + 68 (`nextOffset` 100, 200, 300), `offset: 400` — пусто; без `limit` — все 368 одной страницей (умолчание 500 больше). Расхождений нет.

### Пункт 6 — `plc_get_technology_objects` на ПЛК проверочного проекта (только чтение)

Проверено вживую (`inproc-call`). `PLC (A0)`: один объект — `PID_Compact_1`, `PID_Compact` 2.4, 83 параметра; `PLC (A5)` и `А1.2` (`station_2`): ни одного (`items: []`, «0 technology object(s)»). Параметры объекта:
без `filter` — все 83 (`limit: 0`), `filter: Config.Input` — 9 из 83 (`Config.InputPerOn`, `Config.InputUpperLimit` ...); число параметров в списке совпадает с числом возвращённых значений.
Сверка с деревом: **`plc_get_software_tree` технологических объектов не показывает вовсе** (на верхнем уровне только блоки, типы, теги, таблицы наблюдения и внешние источники), поэтому сверено прямым чтением Openness
(`PlcSoftware.TechnologicalObjectGroup`, включая подгруппы): 1 / 0 / 0 — совпадает с инструментом. Найденное расхождение между деревом и инструментом записано в `../../PLAN.md` («Мелкое»).
Объект каждого «вида» один (только PID); других видов (оси, кулачки) в проекте нет, они проверены на временном CPU в задаче Opus.

### Пункт 3 — `protect_all` / `unprotect_all`

Проверено вживую (временные станции `MCPT_`, удалены). **Не поддерживает ни один CPU, который можно создать из каталога V21**: S7-1500 1511-1 PN V2.9 (раньше, 07.10), 1516-3 PN/DP V4.0, 1511T-1 PN V2.9, 1512SP-1 PN V2.9,
1517H-3 PN V3.1, 1518-4 PN/DP V3.1 и S7-1200 1214C V4.7 — `protect_all`, `protect_all` с паролем и `unprotect_all` везде отвечают одним и тем же текстом TIA Portal: «Additional protection of downloadable
configuration data is not supported»; после отказа `configurationProtection` остаётся `WithoutPassword`. У CPU нет атрибута, который включал бы эту защиту (проверены `Protect*`, `*Secret*`, `*Certificate*`, `Download*` на CPU 1518).
Итог: прочитать обратно результат `protect_all` нельзя ни на каком доступном CPU; вызовы остаются проверенными только отказом. Описание инструмента теперь это говорит (чтобы модель не пробовала по кругу).

### Пункт 1 — кросс-ссылки пользовательских констант

Проверено вживую (временная станция `MCPT_St1`, CPU 1511-1 V2.9; удалена). Таблица `MCPT_TT`, константа `MCPT_Const` = 42 (`plc_create_user_constant`), SCL-функция `MCPT_FCK`
(`#MCPT_FCK := "MCPT_Const" + 1;`), `plc_compile_software` — Success. Служба **есть**: `PlcUserConstant.GetService<CrossReferenceService>()` возвращает её (у таблицы тегов и у самого ПЛК — нет).
Ссылка блока на константу видна в перекрёстных ссылках самого блока (`MCPT_Const`, `PLC tags\MCPT_TT`, доступ `Read`). Но `plc_where_used` и `plc_get_cross_references` по имени и пути константы отвечали
«No block, PLC data type, tag or tag table named ...» — то самое «не найдено», которого задача не допускает. Исправлено: у `plc_get_cross_references` `objectKind: constant` (путь `Таблица/Константа`; в режиме `auto`
константа пробуется последней); таблица тегов и список всего ПЛК включают константы; `plc_where_used` ищет константу, когда ничего другого с таким именем нет, или по `kind: constant`; в `ResolveObjectPath` режим
`any` констант не возвращает (его вызывают экспорт, импорт, перенос: им константы не нужны). После правки: `plc_where_used MCPT_Const` → «used by 1 object(s)» (`MCPT_FCK`, `%FC1`), то же по
`kind: constant`, `kind: tag` честно отвечает «не найдено» (константа не тег); перекрёстные ссылки константы дают источник `MCPT_Const` со ссылкой `MCPT_FCK` (`Read`, `UsedBy`, место `Program code`);
таблица тегов — «0 tag(s) and 1 user constant(s)»; весь ПЛК с `objectKind: constant` — один источник. В `write.json` добавлены константа `MCPT_KX`, SCL-функция, использующая её, `plc_where_used` и таблица
(ждут прогона `smoke.ps1 -Write`).
