## Часть А. Дымовой прогон (сделать первой, она дешёвая)

1. `tools/smoke/` — файлы вызовов только на чтение для тестового проекта: `open_tia_project`,
   `get_project_tree`, `get_devices`, `plc_get_software_tree`, `plc_get_block_info`,
   `get_library_types`, по одному `unified_get_*` на каждый инструмент чтения, на панели и на
   ПК-станции.
2. `tools/smoke.ps1` — выполняет их через `tools/mcp-call.ps1` и печатает сводку: сколько
   вызовов, сколько `isError=True`. Ненулевой код возврата при ошибках.
3. Имена устройств тестового проекта содержат кириллицу (`АРМ Unified`) — файлы JSON хранить
   в UTF-8; `mcp-call.ps1` читает их как UTF-8.
4. Описать в `tools/README.md`: запускать после каждой сборки, которая меняла слой `Siemens/`.

## Часть Б. Категории тестов

Сейчас тесты без TIA отбираются в `tools/finish.ps1` списком исключений по именам классов.
Перевести на категории MSTest: `[TestCategory("NoTia")]` на классах `Test7`..`Test16` (и всех
новых), запуск `dotnet test --filter TestCategory=NoTia`. Обновить `finish.ps1`,
`tests/TiaMcpServer.Test/README.md`.

## Часть В. Эталонный проект (нужно участие Biz)

Интеграционным тестам нужен небольшой проект в репозитории. Создать его через Openness
целиком нельзя (нужны лицензии и ручные шаги), поэтому:

1. Составить для Biz список того, что должно быть в проекте: два ПЛК S7-1500, ET 200SP,
   панель Unified, библиотечные типы (тип данных ПЛК, фейсплейт Unified), мастер-копия, группа
   блоков и станция с `/` в имени, группа устройств, блок во вложенной группе, HMI-теги,
   текстовый список, алармы.
2. Часть объектов сервер может создать сам на заготовке от Biz — это заодно проверка сервера.
3. Архив проекта положить в `tests/TiaMcpServer.Test/assets`; тесты работают на копии во
   временной папке и удаляют её.
4. `Settings.cs`: абсолютные пути заменить на переменную окружения или файл настроек вне git.
5. Починить и дополнить `Test1`..`Test6` под эталонный проект.

Часть В — большая; не начинать без согласия Biz и без готовых частей А и Б.
