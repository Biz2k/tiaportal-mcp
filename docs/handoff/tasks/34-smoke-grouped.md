# 34. «Дымовой» прогон через групповые инструменты

Исполнитель: Sonnet. Приоритет: высокий. Объём: небольшой. Риск для TIA Portal: низкий.

## Зачем

С версии 0.6.0 клиент по умолчанию видит 11 групповых инструментов (`tia_read`, `plc_write`,
...), а оба «дымовых» прогона вызывают инструменты по одному (`--full`). Путь, которым ходят
все пользователи, полным прогоном не проверен ни разу — только короткими вызовами.

## Что известно

- Группы — `ModelContextProtocol/ToolGroups.cs`: `GroupOf(toolName, writes)`, `GroupTool`,
  `HelpTool` (`tia_help` внутри `tia_read`). Вызов: `{"tool": "<имя>", "arguments": {...}}`.
- `tools/mcp-call.ps1` добавляет `--full`, если не задан `-Grouped`. `tools/smoke.ps1` строит
  вызовы из `tools/smoke/read.json`, `write.json`, `inventory.json`.
- Тесты групп — `Test33ToolGroups.cs`.

## Что сделать

1. `tools/smoke.ps1 -Grouped` (сочетается с `-Write`): сервер запускается без `--full`, каждый
   вызов файла заворачивается в группу. Группу инструмента брать у сервера, а не считать в
   скрипте: описания групповых инструментов в `tools/list` называют свои инструменты.
   Инструмент, которого нет ни в одной группе, — ошибка прогона.
2. Проверки прогона остаются те же: ответ без ошибки, `expectError`, `isModified` после чтения,
   инвентаризация до и после, список инструментов без вызова.
3. Дополнительно в режиме `-Grouped`:
   - `tia_help` для каждого инструмента сервера отвечает схемой параметров (172 быстрых вызова);
   - изменяющий инструмент, вызванный через `tia_read`, отклоняется с названием своей группы;
   - инструмент, вызванный через чужую группу записи, отклоняется так же;
   - неизвестное имя — отказ с подсказкой.
4. Прогнать `-Grouped` и `-Grouped -Write` на проверочном проекте. Пока код сервера не менялся,
   новая сборка не нужна и запрос «Openness access» не появится.
5. Расхождения с прогоном `--full` (другой текст ошибки, потерянное поле `meta`, иной вид
   структурированного ответа): дефект обёртки — исправить в `ToolGroups.cs` с тестом; иное —
   записать в план.
6. `tools/README.md`, `tests/TiaMcpServer.Test/README.md`, шаг 6 рабочего цикла в `context.md`.

## Готово, когда

`tools\smoke.ps1 -Grouped -Write` проходит с тем же итогом, что без `-Grouped` (288 из 288 на
07.10.2026, инвентаризация совпадает), и четыре проверки пункта 3 выполняются.

## Результат (08.10.2026)

Сделано: `tools/smoke.ps1 -Grouped` (с `-Write` и без), `tools/mcp-call.ps1 -Grouped -Wrap` (вызовы идут через групповые
инструменты; группа берётся из схемы групповых инструментов сервера, `-GroupsOut` пишет таблицу «инструмент → группа»;
инструмент вне групп — `NOT-IN-ANY-GROUP`, ошибка прогона; вызов с `"raw": true` уходит как есть).

Четыре проверки пункта 3 (175 вызовов): `tia_help` каждого из 172 инструментов отвечает группой (`"callWith"`) и схемой;
изменяющий инструмент через `tia_read` и через чужую группу записи отклоняется с названием своей; неизвестное имя —
отказ со списком. Все прошли.

Прогоны на установленной сборке 0.6.0 (новая сборка и запрос «Openness access» не понадобились):
- `-Grouped`: 50 из 50, проект не изменён, проверки групп 175 из 175.
- `-Grouped -Write`: 288 из 288, 0 ошибок, 0 известных дефектов, 0 инструментов без вызова; инвентаризация — одно
  расхождение, не связанное с обёрткой: `net_get_connections` отдавал поля соединения в **разном порядке** при двух
  одинаковых вызовах (порядок `GetProperties` не гарантирован; воспроизведено и без `-Grouped`). Исправлено сортировкой
  свойств в `Portal.Connections.cs`; три вызова подряд теперь дают один ответ (проверено `inproc-call`).
  Исправление в установленную сборку не входит.

Расхождений обёртки с прогоном `--full` (текст ошибок, `meta`, структурный ответ) не найдено: 288 ответов прошли те же
`expect` / `expectError`.

Ловушка PowerShell 5.1, на которой прогон висел: строка, прочитанная `Get-Content`, несёт свойства провайдера
(`PSPath`, `PSDrive`...), и `ConvertTo-Json -Depth 30` уходит в них практически навсегда. Перед сборкой JSON — `[string]`.
