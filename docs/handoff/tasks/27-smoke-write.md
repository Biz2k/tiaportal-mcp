# 27. «Дымовой» прогон записи и проверка «чтение не меняет проект»

Исполнитель: Sonnet. Приоритет: высокий — это страховка для всего остального.
Объём: средний. Риск для TIA Portal: средний — прогон вызывает все изменяющие инструменты.

Этап 1 Opus закрыт 06.10.2026: в прогон входят `plc_replace_source` (удачная замена, замена
с ошибкой и возвратом прежнего кода) и `unified_compile` (после записи скриптов и формул —
ошибок на временном экране быть не должно). Изменяющие инструменты Unified теперь отказывают
на значения, которые не проходят проверку TIA Portal: вызовы прогона должны быть полными
(скрипт-динамизация — с триггером).

## А. Чтение не меняет проект

Случай уже был: транзакция, открытая ради чтения, делала проект «изменённым».

1. `tools/smoke.ps1`: первым и последним вызовом читать признак изменённости проекта
   (`get_project` / `get_state` — найти, где он есть; если его нет в ответе, добавить поле
   `isModified`). Расхождение — ошибка прогона. Чтобы назвать виновника, при расхождении
   повторить прогон, читая признак после каждого вызова.
2. Прогон выполнять на сохранённом проекте; если проект изменён до начала — сказать это и
   выйти с кодом 2, не сохраняя самому.

## Б. Прогон записи

`tools/smoke.ps1 -Write` с файлом `tools/smoke/write.json`: по одному удачному вызову
**каждого** инструмента с `[WriteTool]`, на объектах с префиксом `MCPT_`, с уборкой.

1. Список изменяющих инструментов взять из собранного сервера (`tools/mcp-call.ps1
   -DumpTools`; у изменяющих в аннотациях `readOnlyHint: false`). Скрипт сверяет список с
   файлом вызовов и называет инструменты без вызова — так новый инструмент не останется без
   проверки.
2. Порядок: создать → изменить → прочитать и сравнить → удалить. Для ПЛК завести временное
   устройство `MCPT_PLC` (`hw_create_device`) и работать в нём, не в рабочих ПЛК. Для Unified —
   панель `HMI Unified/HMI_RT_3` **и** ПК-станция `АРМ Unified/HMI_RT_1`: запись на станции
   проверена только для алармов; экраны и группы экранов, скрипты, архивные теги,
   динамизации, настройки runtime там не проверялись.
3. Каждое записанное значение, которое Openness может исказить молча (формула, выражение,
   текст списка, код скрипта), читать обратно отдельным вызовом и сравнивать в скрипте.
4. Не входят в прогон: `download_to_plc` (нужен PLCSIM, его запускает Biz), `save_as_project`,
   `close_project`, `open_project` — для них отдельный файл `tools/smoke/project.json`,
   запускаемый вручную на копии проекта.
5. После прогона: инвентаризация «до» и «после» совпадает (число блоков, тегов, экранов,
   алармов, списков). Проект **не сохранять** — так следы неудачной уборки не попадут на диск.
   Модули скриптов Openness удалять не умеет: использовать один и тот же `MCPT_Mod`,
   перезаписывая его пустым.
6. Найденные дефекты не чинить в этом же коммите: записать в `../../PLAN.md`, раздел 1, и
   чинить отдельно. Дефект в инструментах этапа 1 Opus — только записать.

## Готово, когда

- `tools/smoke.ps1` (чтение) сообщает, изменился ли проект.
- `tools/smoke.ps1 -Write` проходит на проверочном проекте; после него в проекте нет объектов
  `MCPT_`, кроме модуля скриптов.
- `tools/README.md` описывает оба режима; в рабочем цикле `../context.md` — «после изменения
  слоя `Siemens\` прогнать оба».
- В `../../PLAN.md` отмечены «дымовой прогон записи», «чтение не меняет проект», «запись на
  ПК-станции».
