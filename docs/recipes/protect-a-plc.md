# Protect a PLC

What protects a CPU, and in which order to set it. Everything here changes the protection of a device: say in plain words what will change on which CPU and get the user's yes before each call. A password is one the user gave in this conversation; in the examples below it is written `<password the user gave>`. Never make one up, never repeat it in an answer. The server passes it to TIA Portal and keeps it nowhere. A password with a space in it is refused by the CPU (a bare `EngineeringPasswordPolicyViolationException`): ask for another one.

`sec_protect_project` (the password of the whole project) is not part of this recipe and is not to be called to try it out: TIA Portal cannot undo it, and a lost password locks the project.

1. Read the state: `sec_get_plc_security` with `deviceItemPath` (`<station>/<CPU>`, found with `hw_get_devices`). It names the CPU, `configurationProtection`, and, depending on the firmware, `accessLevel` and `webserverUsers` (CPU older than V4) or `accessControl` (V4 and newer), `opcUaUsers`, and `notes` that say what this CPU does not have.
2. Protect the confidential configuration data: `sec_set_plc_configuration_protection` with `action` `protect` and a `password`. `unprotect` needs the same password and is refused without it ("not provided"). A new CPU does not compile until this and, on a CPU older than V4, the full-access password of step 3 are set: `hw_compile` reports three errors (password for full access, password for confidential data, communication certificate). The answer shows `before` and `after`.
3. CPU with firmware older than V4 (checked on a 1511-1 PN V2.9): the access level. `sec_set_plc_access_level` with `accessLevel` - what is allowed WITHOUT a password: `FullAccess`, `ReadAccess`, `HMIAccess` or `NoAccess` (a wrong level locks people out) - and the password that opens a level in `passwordFor` + `password` (set `FullAccess` first). `resetPasswordFor` removes a password again. On a CPU of V4 or newer the call is refused with an explanation: there the access is decided by users and roles (step 6).
4. Web server, older CPU: switch it on first, `hw_set_device_item_attributes` on the CPU with `{"WebserverActivate": true}` (without it `sec_manage_webserver_users` says so and changes nothing). Then `sec_manage_webserver_users` with actions `create` / `update` / `delete`, `userName`, `permissions` (`DoDiagnosis`, `ReadTag`, ...), `password`. `sec_get_plc_security` lists them as `name: permissions`. A CPU of V4 or newer has no web server users of its own; it takes those of the project.
5. OPC UA users and the display password. Both are refused while the protection they belong to is off, and the refusal says what to switch on:
   - OPC UA, older CPU: `hw_set_device_item_attributes` on `<CPU>/OPC UA_1` with `{"OpcUaServer": true}`, then in a second call `{"OpcUaPasswordAuthentication": true}`; then `sec_manage_opcua_users` (`create`, `userName`, `password`). On a CPU of V4 or newer the attribute `OpcUaPasswordAuthentication` does not exist; OPC UA access is a right of a project user (step 6, right `OPCUAServerAccess`), and `hw_compile` asks for at least one user with it once the OPC UA server is on.
   - Display: `hw_set_device_item_attributes` on `<CPU>/CPU display_1` with `{"DisplayProtection": true}`, then `sec_set_display_password`. Works on both generations.
6. CPU of V4 or newer: users and roles of the project. `sec_get_project_users` lists users, groups, roles and the password policy; with `rightsOfDevice` (the station name) it also lists what the device offers as rights (`availableRights`: `ProtectionLevelReadAccess`, `WebAllowDiagnostics`, `OPCUAServerAccess` ...). `sec_manage_project_roles` creates a role with `device` and `addRights` (a system role cannot be changed; deleting a role takes it away from its users), `sec_manage_project_users` creates a user or a group with `roles` and a `password`. Whether the CPU asks for them is the attribute `PlcAccessControlConfiguration` of the CPU, set with `hw_set_device_item_attributes`. It takes effect in the PLC after a hardware compile and a download.
7. Blocks: `sec_set_block_protection` with `softwarePath`, `blockPath`, `action` `protect` / `unprotect` and a `password` makes a block know-how protected and writes its protection back.
8. `hw_compile` of the station, then `save_project` when the user wants it kept.

Which steps apply:

| Firmware of the CPU | 2 configuration data | 3 access level | 4 web server users | 5 OPC UA users | 5 display | 6 users and roles | 7 blocks |
|---|---|---|---|---|---|---|---|
| older than V4 (checked V2.9) | yes | yes | yes | yes (two-step switch-on) | yes | - | yes |
| V4 and newer (checked V4.0) | yes | refused (none) | refused (project users) | project right `OPCUAServerAccess` | yes | yes | yes |

To undo: `sec_set_plc_configuration_protection` `unprotect` with the password, `sec_set_plc_access_level` with `resetPasswordFor`, `sec_manage_webserver_users` / `sec_manage_opcua_users` `delete`, `sec_manage_project_users` and `sec_manage_project_roles` `delete`, the attributes back to `false`. Every write is in memory until `save_project`.

Checked live on V21 (08.10.2026) with temporary stations: steps 1-5 on a CPU 1511-1 PN V2.9 (with the refusals quoted above), steps 1, 2, 5 (display) and 6 on a CPU 1516-3 PN/DP V4.0 (role with rights on the device, user with the role, both deleted again), and the compile before and after step 2. Not checked: the effect in a running CPU (needs a download), the step with `PlcMasterSecretPassword`, a V4 CPU that asks the user for a login at the connection, OPC UA users of a V4 CPU (the license check of `hw_compile` stops there: "the configured OPC UA license is not sufficient").
