## Этап 1. Диагностика ошибок (замечания 2, 3, 5, 6)

### 1.1. Не терять сообщение Openness

Причина (подтверждено): `Operation.Decorate` в `Siemens/Operation.cs` оборачивает любое

`InnerException` и до модели не доходит.

- [x] В `Operation.Decorate` включать в сообщение текст исходного исключения, включая

### 1.2. Убрать «общую ошибку вызова»

Причина (гипотеза): `get_project`, `get_devices` и `get_device_item_info` кладут в ответ

после выхода из метода, вне его `try/catch`, и SDK отдаёт безликое сообщение. У блоков
атрибуты примитивные, поэтому `get_block_info` работает.

- [x] В `Helper.GetAttributeList` приводить значения к безопасным для JSON: примитивы и
      строки как есть, перечисления и даты строкой, `FileInfo`/`DirectoryInfo` — путь,
      коллекции — список, остальное — `ToString()` (`Helper.ToJsonSafe`).
- [x] Читать каждый атрибут в своём `try/catch`, чтобы один сбойный атрибут не ронял весь
      ответ.

## Этап 2. Единое разрешение путей (замечания 1 и 7)

### 2.1. Блоки во вложенных группах

Причина (подтверждено на проекте, см. результаты этапа 0): группа называется
`Inputs/Outputs` — TIA Portal допускает `/` в именах групп. `GetBlockPath` склеивает сегменты через `/` без
экранирования, а `NormalizeGroupPath` и `WalkGroups` режут путь по каждому `/`. В итоге
листинг и `plc_resolve_object_path` возвращают путь, который обратно не разбирается.
Косвенное подтверждение: блоки в обычных группах и в корне находятся.

- [x] Проверить на проекте имя группы (`plc_get_software_tree`).
- [x] Ввести экранирование `/` внутри сегмента в одном месте. Выбрано `%2F`, а не `\/`:
      `NormalizeGroupPath` уже трактует `\` как разделитель, а `//` как пустой сегмент.
      Построение пути: `BuildGroupPath`, `JoinLeaf` (блоки, типы, таблицы тегов, таблицы
      наблюдения, внешние источники, теги). Разбор: `PathSegments`, `SplitPath`,
      `WalkGroups` (`Siemens/Software/Portal.Software.Resolve.cs`).
- [x] Запасной механизм при разборе: если сегмент не найден как написан, он склеивается
      со следующими через `/` (`WalkNamed`). Путь `Inputs/Outputs/AI_Handler` находит блок
      без экранирования. Отличие от первоначального замысла: при двух прочтениях
      побеждает буквальная структура (группа `Inputs` с подгруппой `Outputs`), а не
      выдаётся ошибка неоднозначности; вторую группу адресует экранированная форма.
- [x] `GetBlock` и `GetType` сначала ищут точное имя и только потом трактуют его как
      регулярное выражение (`FindByName`).
- [ ] При `NotFound` везде предлагать кандидатов через `ResolveObjectPath`. Не сделано:
      мест возврата «не найдено» несколько десятков, а после запасного механизма

## Этап 3. Создание, копирование и перемещение блоков (замечания 3, 4, 5)

### 3.1. `plc_create_fb` и `plc_create_instance_db`

Причины (подтверждено на проекте, см. результаты изменяющих сценариев):

- `PlcBlockComposition.CreateFB` в Openness создаёт только ProDiag-FB. Для `LAD`, `SCL` и
  прочих языков вызов всегда отклоняется, номер блока здесь ни при чём.
- `CreateInstanceDB` при `autoNumber = true` и `number = 0` создаёт `DB0`. Проверки номера
  в коде не было.

- [x] `plc_create_fb`: ProDiag — через `CreateFB`; SCL — генерация из текста источника
      (`GenerateFromSclText`); LAD, FBD, STL — импорт минимального документа SimaticML
      (`BuildFbTemplate`); остальные языки — отказ `NotSupported` с объяснением.
- [x] До вызова: при `autoNumber = false` номер должен быть от 1 и свободен, иначе
      `InvalidParams` с ближайшим свободным номером (`ResolveBlockNumber`).
- [x] При `autoNumber = true` сервер сам подбирает первый свободный номер.
- [x] `plc_create_instance_db` проверяет до создания, что FB `instanceOfName` существует.
- [x] Проверка, что имя блока в ПЛК свободно, до любых изменений.

## Этап 4. Диагностика `download_to_plc` (замечание 6)

Причина (подтверждено, `Portal.Download.cs` и `McpServer.Download.cs`):

- Из `DownloadResult` берутся только `State`, `ErrorCount`, `WarningCount`; дерево
  `Messages` не читается.
- Предварительная конфигурация задаётся через `dynamic` с пустым `catch`, поэтому
  необработанный шаг (остановка модулей, перезапись и т. п.) молча срывает загрузку.
- Исключение Openness превращается в `DownloadToPlc failed` (исправляется этапом 1).

Что сделано:

- [x] `DownloadResult.Messages` собираются рекурсивно в ответ; информационные строки
      ограничены параметром `maxMessages` (по умолчанию 40), ошибки и предупреждения
      возвращаются всегда.
- [x] `dynamic` с пустым `catch` заменён разбором шагов конфигурации через отражение
      (`AnswerDownloadStep`): для каждого шага возвращаются тип, текст TIA Portal, варианты
      и данный ответ. Шаг, для которого у сервера нет ответа, остаётся с предустановкой
      TIA Portal и явно перечисляется в ответе.
- [x] В ответе: цель (режим, интерфейс ПК, целевой интерфейс), что загружалось, шаги,
      сообщения. При сбое в тексте ошибки — стадия и увиденные шаги.
- [x] Явные флаги `stopPlc` и `startPlc`, оба по умолчанию `false`. Если загрузка требует
      остановки CPU, а `stopPlc` не задан, возвращается отказ с этим объяснением.
- [x] Параметр `selections` (`ТипШага=Вариант`) для ответа на шаг иначе, чем по умолчанию.
- [x] В описании инструмента указано, что цель должна быть запущена заранее.
- [ ] Отдельные итоги по аппаратной и программной части не выделялись: они видны в дереве
      сообщений (`Hardware configuration`, `Software configuration`).
- [x] Режим проверки без загрузки — **отменён**, см. ниже.

### Инцидент 05.10.2026: «пробный прогон» закрыл TIA Portal

Первая реализация включала `dryRun`: загрузка прерывалась исключением из первого
обратного вызова конфигурации, до начала записи. Openness превращает исключение,
брошенное внутри обратного вызова загрузки, в `NonRecoverableException` и закрывает
экземпляр TIA Portal. При проверке в 21:08 так был закрыт TIA Portal пользователя с
открытым тестовым проектом; несохранённые изменения потеряны. Последующий `connect` для
проверки состояния запустил новый пустой экземпляр, потому что `ConnectPortal` стартует
TIA Portal, если ни один не запущен.

Выводы, отражённые в коде:

- `dryRun` удалён. Предварительно посмотреть шаги загрузки, не начав её, через Openness
  нельзя: увидеть следующий шаг можно, только ответив на предыдущий.
- Обратные вызовы загрузки не выпускают исключений; `AnswerDownloadStep` ловит всё сам.
  В `Portal.Download.cs` оставлен комментарий с причиной.

Открытый вопрос (в план этапа 6): `connect` молча запускает новый TIA Portal, когда нет
запущенного. Для сервера, которым управляет модель, это неожиданный побочный эффект;
стоит сделать запуск явным параметром.
