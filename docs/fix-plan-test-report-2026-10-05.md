## Этап 1. Диагностика ошибок (замечания 2, 3, 5, 6)

### 1.1. Не терять сообщение Openness

Причина (подтверждено): `Operation.Decorate` в `Siemens/Operation.cs` оборачивает любое

`InnerException` и до модели не доходит.

- [x] В `Operation.Decorate` включать в сообщение текст исходного исключения, включая
      вложенные `EngineeringException` и их `MessageData`, если они есть

- [x] Вынести формирование текста ошибки для клиента в один помощник в `McpServer.cs`

### 1.2. Убрать «общую ошибку вызова»

Причина (гипотеза): `get_project`, `get_devices` и `get_device_item_info` кладут в ответ

после выхода из метода, вне его `try/catch`, и SDK отдаёт безликое сообщение. У блоков
атрибуты примитивные, поэтому `get_block_info` работает.

- [x] В `Helper.GetAttributeList` приводить значения к безопасным для JSON: примитивы и
      строки как есть, перечисления и даты строкой, `FileInfo`/`DirectoryInfo` — путь,
      коллекции — список, остальное — `ToString()` (`Helper.ToJsonSafe`).
- [x] Читать каждый атрибут в своём `try/catch`, чтобы один сбойный атрибут не ронял весь
      ответ.
- [x] Проверить гипотезу на живом проекте. Подтверждена 05.10.2026: на новой сборке

## Этап 2. Единое разрешение путей (замечания 1 и 7)

### 2.1. Блоки во вложенных группах

Причина (подтверждено на проекте, см. результаты этапа 0): группа называется
`Inputs/Outputs` — TIA Portal допускает `/` в именах групп. `GetBlockPath` склеивает сегменты через `/` без
экранирования, а `NormalizeGroupPath` и `WalkGroups` режут путь по каждому `/`. В итоге
листинг и `plc_resolve_object_path` возвращают путь, который обратно не разбирается.
Косвенное подтверждение: блоки в обычных группах и в корне находятся.

- [x] Проверить на проекте имя группы (`plc_get_software_tree`).
- [ ] Ввести экранирование `/` внутри сегмента (например, `\/`) в одном месте: построение
      пути (`BuildGroupPath`, `GetBlockPath`, аналоги для типов, тегов, таблиц наблюдения,
      внешних источников) и разбор (`NormalizeGroupPath`, `SplitPath`, `WalkGroups`,
      `GetBlock`).
- [ ] Запасной механизм при разборе: если путь не найден буквально, попробовать склейку
      соседних сегментов и вернуть объект только при единственном совпадении.
- [ ] В `GetBlock` имя сейчас трактуется как регулярное выражение, если в нём есть `.`,
      `(`, `+` и т. п. Для точных путей сначала искать точное совпадение, и только потом
      регулярное выражение.
- [ ] При `NotFound` везде предлагать кандидатов через `ResolveObjectPath`.

### 2.2. Устройства и элементы устройств

Причина (подтверждено):

- `GetDeviceByPath` и `GetDevices` в `Portal.Devices.cs` не смотрят в
  `UngroupedDevicesGroup`, где лежат станции распределённой периферии.
- Дерево проекта показывает имя элемента (`PLC (A0)`), а `GetDeviceByPath` ищет по
  `Device.Name` (например, `S7-1500/ET200MP station_1`), которое к тому же содержит `/`.
- `hw_*` и `net_*` принимают имя устройства и ищут через `Devices.Find`, без групп;
  остальные инструменты принимают путь.

Что сделать:

- [ ] Один разрешатель устройства: принимает и путь из дерева, и `Device.Name`, обходит
      `Devices`, `DeviceGroups` рекурсивно и `UngroupedDevicesGroup`, учитывает
      экранирование из 2.1.
- [ ] Перевести на него `hw_get_device_info`, `get_device_item_info`, `get_devices`,
      `GetSoftwareContainer` и все `hw_*`/`net_*`.
- [ ] `get_project_tree`, `get_devices` и `get_hardware_topology` должны возвращать для
      каждого узла поле `path`, которое принимается всеми остальными инструментами.

Критерий готовности этапа: любой путь из листинга принимается любым инструментом той же
области без правки руками.

## Этап 3. Создание, копирование и перемещение блоков (замечания 3, 4, 5)

### 3.1. `plc_create_fb` и `plc_create_instance_db`

Причины (подтверждено на проекте, см. результаты изменяющих сценариев):

- `PlcBlockComposition.CreateFB` в Openness создаёт только ProDiag-FB. Для `LAD`, `SCL` и
  прочих языков вызов всегда отклоняется, номер блока здесь ни при чём.
- `CreateInstanceDB` при `autoNumber = true` и `number = 0` создаёт `DB0`. Проверки номера
  в коде нет.

Что сделать:

- [ ] `plc_create_fb`: для языков, отличных от ProDiag, создавать FB через генерацию из
      SCL-источника (как `plc_create_scl_block`) или импорт XML-шаблона; путь через
      `CreateFB` оставить только для ProDiag. Обновить описание инструмента и раздел
      ограничений в `README.md`.
- [ ] До вызова: при `autoNumber = false` требовать номер ≥ 1 и проверять, что он не
      занят; иначе `InvalidParams` с перечнем ближайших свободных номеров.
- [ ] При `autoNumber = true` передавать в Openness допустимый номер (первый свободный),
      а не 0.
- [ ] Для `plc_create_instance_db` проверять до создания, что FB `instanceOfName`
      существует.
- [ ] После создания проверять `block.Number`; при 0 удалять объект и возвращать ошибку.
      При работе в транзакции достаточно бросить исключение — изменение откатится.
- [ ] Возвращать в ответе фактический номер блока.

### 3.2. `plc_copy_block`, `plc_copy_type`

Причина (подтверждено по алгоритму): копия делается экспортом и импортом того же XML в тот
же ПЛК. Имя блока и имя типа уникальны в пределах ПЛК, номер блока тоже. Импорт без
`Override` обязан упасть, а с `Override` заменяет оригинал, а не создаёт копию. То есть в
текущем виде копирование внутри одного ПЛК работать не может.

- [ ] Добавить обязательный для копии внутри ПЛК параметр `newName`; переименование делать
      правкой экспортированного XML (имя и сброс номера на автоназначение).
- [ ] Добавить необязательный `targetSoftwarePath` для копирования в другой ПЛК, где
      исходное имя можно сохранить.
- [ ] Без `newName` и при том же ПЛК — сразу `InvalidParams` с объяснением.
- [ ] Обновить описания инструментов и раздел ограничений в `README.md`.

### 3.3. `plc_move_block`, `plc_move_type`

Причина та же: импорт выполняется до удаления оригинала и конфликтует с ним по имени.

- [ ] Порядок: экспорт → удаление оригинала → импорт в целевую группу.
- [ ] Страховка: всё внутри одной транзакции; если транзакция недоступна — при сбое
      импорта вернуть блок в исходную группу из того же файла, и только потом удалять
      временный каталог.
- [x] Проверить гипотезу, что экспорт или импорт запрещены внутри
      `ExclusiveAccess`-транзакции. Не подтвердилась: импорт внутри транзакции
      выполняется, а откат после сбоя сработал.
- [ ] Параметр `overwrite` у перемещения убрать или переопределить: сейчас импорт с
      `Override` заменяет оригинал на месте, и последующее удаление падает.

### 3.4. `plc_compile_block`

Новый дефект из проверки 05.10.2026: для SCL FB инструмент отвечает
`Block ... is not compilable`, хотя `plc_compile_software` компилирует тот же блок.

- [ ] Разобраться, почему для блока не находится служба компиляции, и исправить.
- [ ] Перед началом проверять согласованность и защиту know-how (уже есть) и сообщать
      стадию, на которой произошёл сбой.

Критерий готовности этапа: сценарии создания FB и экземплярного DB, копии с новым именем
и перемещения между группами проходят на тестовом ПЛК и компилируются без ошибок.

## Этап 4. Диагностика `download_to_plc` (замечание 6)

- Из `DownloadResult` берутся только `State`, `ErrorCount`, `WarningCount`; дерево

  необработанный шаг (остановка модулей, перезапись и т. п.) молча срывает загрузку.
- Исключение Openness превращается в `DownloadToPlc failed` (исправляется этапом 1).
